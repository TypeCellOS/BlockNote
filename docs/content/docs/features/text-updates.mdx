# Text Updates

With text updates, a client can read a document as markdown, HTML or plain text, change the text, and write it back. An example is an AI agent or a script that edits documents as text, or an HTTP API with a `GET` and a `PUT` for each format.

A write does not replace the document. It applies only the changes of the text. Block IDs, colors, alignment, styles that the format does not show, nesting, and comments on text that did not change stay.

## Installation

```bash
npm install @blocknote/xl-ai
```

The text updates are in the `@blocknote/xl-ai/text-lens` entry point. On a server, the markdown and HTML conversions need a DOM (see [Server-side Processing](/docs/features/server-processing)). For a Y.Doc, also install `@y/y` and `@y/prosemirror` (Yjs 14, see [Y.Doc](#ydoc)).

## Read and Write Text

```typescript
import { BlockNoteEditor } from "@blocknote/core";
import {
  getDocumentText,
  markdownFormat,
  updateDocument,
} from "@blocknote/xl-ai/text-lens";

const editor = BlockNoteEditor.create({ initialContent });

// Read the document as markdown.
const markdown = getDocumentText(editor, markdownFormat);

// A client changes the markdown. Then write it back.
const result = updateDocument(editor, {
  format: markdownFormat,
  text: changedMarkdown,
  base: "current", // the client read the current document
});
if (result.error === undefined) {
  const { operations, warnings } = result;
}
```

`base` is the version that the client read. `"current"` is correct if no other writer can change the document between the read and the write, for example if the read and the write occur in the same tick. Else, give the version that the client read (see [Concurrent Writes](#concurrent-writes)).

`updateDocument` applies the changes in one transaction. `operations` lists the changes by block ID, and `warnings` lists changes that did not apply as written (see [Warnings](#warnings)). To compute the operations, but not apply them, use `computeOperations` with the same change. Then `applyOperations(tr, operations)` applies them to a transaction of your own, for example to show them as suggestions.

If the text gives blocks that do not fit the schema of the editor, the result is `{ error: "invalid-document" }`, and the document does not change. An example is an HTML table cell that spans more rows than the table has.

The formats are `markdownFormat`, `htmlFormat` and `plainTextFormat`. HTML shows more data than markdown (for example colors and underline), thus a client can also change that data. In HTML, some data shows two times: as a `data-*` attribute and in the visible markup (for example `data-text-alignment` and `style="text-align: …"`, or `data-caption` and `<figcaption>`). The parse reads the attribute. Thus, to change such data, change the `data-*` attribute too.

If your document is in a Y.Doc, read [Y.Doc](#ydoc) first: the function to use depends on the writer.

## Which Block Is the Same Block

The text does not contain block IDs. The identity of a block follows the location of its text:

1. A block with the same text is the same block. A block that the text moves keeps its ID and props, if no other block has the same text.
2. A changed block is the same block if it shares at least half of the letters and digits of the shorter text. Thus, a paragraph with many new sentences keeps its ID and props. A changed block that also moved must share at least half of the longer text.
3. If one block on each side stays between two pairs, the two blocks are the same block. Thus, a paragraph with fully new text at the same position keeps its ID.

If blocks change places, the blocks with the most text in common stay in place, and the other blocks are the moved blocks. Thus, if a short block moves past changed paragraphs, the changed paragraphs keep their IDs.

The same text is a stronger sign than similar text or a position. If an edit changes a block and adds a block with its old text at a different place, the block with the old text keeps the ID, and the changed block is a new block. A block that the text moves and changes more than this is a new block.

A split paragraph keeps its ID on the part with most of its text. Two joined paragraphs keep the ID of the first paragraph.

## Concurrent Writes

A client can take time to change the text, for example an AI agent. Other users can change the document in that time. Give the document at the version that the client read as `base`. Then the write applies only if the document is still at that version:

```typescript
import {
  getDocumentText,
  markdownFormat,
  updateDocument,
} from "@blocknote/xl-ai/text-lens";

const { text, base } = {
  text: getDocumentText(editor, markdownFormat),
  base: editor.document, // keep this version, for example in your version history
};

// ... later, after the client changed the text:
const result = updateDocument(editor, {
  format: markdownFormat,
  text: changedText,
  base,
});
if (result.error === "document-changed") {
  // Other users changed the document after `base`. Nothing applied.
  // result.changesOfOthers: the blocks that they changed.
}
```

This write is strict, and it is the recommended way to write from an older version. If other users changed the document after `base`, the result is the error `document-changed`, and the document does not change. The error lists the blocks that the other users changed in `changesOfOthers` (`{ id, change: "added" | "changed" | "moved" | "removed" }`). Then read the document again, make the change in the new text, and write again. For an AI agent, send the current text together with the error, so that the agent can make its change again.

The write compares the full documents, also the data that the format does not show (for example a color in markdown). Thus, `base` must be the full document (BlockNote JSON) of that version, as `editor.document` gives it. You can keep it as JSON in a database. A version history keeps full documents anyway, because only a full document shows props and nesting.

With `base: "current"`, there is no check. The text applies to the current document, thus a text from an older version changes the newer changes back.

### Merge With the Changes of Other Users

<Callout type="warning">
  The merge is experimental. Its rules can change, and it has known wrong
  results (see below). Prefer the strict write, and use the merge with
  `onConflict: "reject"`.
</Callout>

With many users, a strict write can fail often: it also fails for a change far from the text of the client. `updateDocumentWithMerge` (and `computeOperationsWithMerge`) merges the change of the client with the changes that other users made after `base`:

```typescript
import {
  markdownFormat,
  updateDocumentWithMerge,
} from "@blocknote/xl-ai/text-lens";

const result = updateDocumentWithMerge(editor, {
  format: markdownFormat,
  text: changedText,
  base, // the document at the version that the client read
  onConflict: "reject",
});
if (result.error === "conflict") {
  // result.conflicts: the warnings `conflicting-change`, `removed-changed-block`
  // and `change-to-removed-block`, with the block IDs. Nothing applied.
} else if (result.error === undefined) {
  const { operations, warnings, changesOfOthers, written } = result;
}
```

The client's changes apply to the current document, by block ID, and the changes of the other users stay. A conflict is a part of a block that both sides changed in different ways (for example the same words, or the same prop), or a block that one side removed and the other side changed. `onConflict` is required, and tells what a conflict does:

- `"reject"`: the write changes nothing, and the result is the error `conflict`, with the conflicts. The client can show them, or read the document again.
- `"keep-current"`: the change of the other user stays, and the client gets a warning (see [Warnings](#warnings)). The other changes of the client apply.

The result of a merge that applies has two more fields:

- `changesOfOthers`: the blocks that other users changed after `base`. The document after the write has these changes too. Give this list to an AI agent, so that it knows which changes it did not make.
- `written`: the document as the client wrote it, without the changes of the other users. If the client writes again and did not read the document again, give `written` as the `base` of that write. Do not give the document after the write as the `base` of a text that the client did not read from it: that write removes the changes of the other users, without a warning.

Known wrong results of the merge:

- With `"keep-current"`, a text can show two times. This occurs if the client splits or joins paragraphs, and another user changes the text that moves to the other paragraph.
- A merge without a conflict can give a value that no user wrote. If two users change different words of one sentence, the two changes stay, and the sentence is a mix of the two.

The merge becomes stable after a review of its rules, a decision about the identity of blocks, a contract for `written` (also for a Y.Doc), and use in one real product.

## BlockNote JSON

Each write function also takes a full document as BlockNote JSON: `{ document, base }` in place of `{ format, text, base }`. The JSON contains the block IDs, thus the blocks pair by ID. Only the changed blocks and fields change. A field that the JSON of a block does not have gets its default value, thus send each block with all its fields:

```typescript
import { updateDocument } from "@blocknote/xl-ai/text-lens";

const result = updateDocument(editor, {
  document: changedBlocks,
  base, // "current", or the document at the version that the client read
});
```

A block without an ID is a new block. An ID can identify only one block. Thus, a document with two blocks with one ID gives the error `invalid-document`. In a merge (`updateDocumentWithMerge`), a block also gets a new ID if another user added a block with that ID after the client read the document.

If the JSON does not fit the schema of the editor, the result is `{ error: "invalid-document" }`, as for a text. Examples are an unknown block type or style, and a prop value that the block type does not have.

## Y.Doc

A collaborative document is in a Y.Doc (Yjs 14, `@y/y`). There are two ways to write to it. The correct one depends on the writer, not on where the code runs.

| The writer | Read | Write | `base` |
| --- | --- | --- | --- |
| The user of an editor that is bound to the Y.Doc (for example a command of your app that the user starts) | `getDocumentText(editor, format)` | `updateDocument(editor, change)`, on that editor | `"current"`, or `editor.document` at the read |
| Each other writer (a server, an agent, an import) | `getYDocText(editor, fragment, format)` | `updateYDoc(editor, fragment, change)` | `"current"`, or `Y.encodeStateAsUpdateV2(ydoc)` at the read |

Read and write with the functions of one row. The two rows read the document in different ways, and they take a different `base`.

The differences:

- **Undo.** A write with `updateDocument` is a change of the user of that editor, and one undo of the editor reverts it. A write with `updateYDoc` is not a change of the user of an editor: the undo of an editor does not revert it.
- **The editor.** `updateDocument` needs the mounted editor of the user. For `updateYDoc`, the editor gives only the schema and the conversions: it is not bound to the Y.Doc, and it needs no view. Thus, `updateYDoc` also runs on a server.
- **Suggestions and version comparisons.** Do not use `updateDocument` while the editor shows suggested changes or a comparison of two versions. The editor then also contains the removed text, with a mark, and the write reads that text as content. `updateYDoc` reads the Y.Doc, thus it gets the document without these marks.

### Write to the Y.Doc

For a writer that is not the user of a bound editor, use the functions of the `@blocknote/xl-ai/text-lens/y` entry point. `getYDocText` reads the text, and `updateYDoc` takes the same change as `updateDocument` (a text or BlockNote JSON). The editor gives only the schema and the conversions of the formats. It does not have to be bound to the Y.Doc, and it needs no view: the lens writes to the Y.Doc without an editor view. An editor that is bound to the Y.Doc gets the write as a change of another writer. The write is one Yjs transaction of the Y.Doc, with the client ID of that Y.Doc. `base` is `"current"`, or the Yjs state of the version that the client read:

```typescript
import { BlockNoteEditor } from "@blocknote/core";
import * as Y from "@y/y";
import { markdownFormat } from "@blocknote/xl-ai/text-lens";
import { getYDocText, updateYDoc } from "@blocknote/xl-ai/text-lens/y";

const fragment = ydoc.get("document-store");
// An editor with the schema and the extensions of your other clients.
const editor = BlockNoteEditor.create();

const text = getYDocText(editor, fragment, markdownFormat);
// The V2 update format, as the versions of BlockNote use it.
const base = Y.encodeStateAsUpdateV2(ydoc);

// ... later:
const result = updateYDoc(editor, fragment, {
  format: markdownFormat,
  text: changedText,
  base,
});
if (result.error === undefined) {
  // Send `result.updateV2` to the other clients, if no provider does that.
  // It is a V2 update: they apply it with `Y.applyUpdateV2`.
}
```

Give the editor the same schema and extensions as your other clients (for example comments). If the schema cannot read the content of the Y.Doc, the write throws, and the Y.Doc does not change.

A Yjs state as `base` is a V2 update: `Y.encodeStateAsUpdateV2(ydoc)`. A V1 update (`Y.encodeStateAsUpdate`) is not a valid `base`: Yjs throws for it, and the Y.Doc does not change.

`updateYDoc` is strict, as `updateDocument`: with a Yjs state as `base`, the write applies only if the document is still at that version. Else the result is the error `document-changed`, with `changesOfOthers`. A change in a different part of the Y.Doc (not in the fragment of the document) does not stop the write.

`updateYDocWithMerge` is the [merge](#merge-with-the-changes-of-other-users) for a Y.Doc, with a Yjs state as `base` and a required `onConflict`. Its result has no `written`. Thus, after a write with `changesOfOthers`, read the text again before the next write. In a Y.Doc, a move is a removal and an insert: if two users move the same block at the same time, the block can be there two times.

With `experimental_updateYDocWithYjsMerge`, Yjs merges the write instead. The changes of the client apply to a copy of the Y.Doc at `base`, and Yjs merges that copy into the Y.Doc. This function takes a Yjs state as `base`. It has no `onConflict`, because Yjs merges without conflicts. It has more limits. A change of another user can be lost if the client moves, splits or joins the block, or changes its type. Also, a block that the client removes goes, with the changes of other users in it.

## Warnings

A result can contain these warnings. Only a merge gives the warnings about another user:

| Warning                     | Meaning                                                                                                                                                                     |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `block-shape-replaced`      | The format shows the block with content of another shape (for example a file without a caption as a link), and the text changed it. It becomes a block of the text.         |
| `change-to-removed-block`   | The client changed or moved a block that another user removed. The change does not apply.                                                                                   |
| `removed-changed-block`     | The client removed a block that another user changed (or a block in it). The blocks with a change of the other user stay.                                                  |
| `conflicting-change`        | The client and another user changed the same part of a block (a part of its text, a style, a prop, its parent or its place). The change of the other user stays there.     |
| `merged-cells-removed` | A table lost its merged cells. Markdown and plain text show merged cells as separate cells, thus a change of the table there removes them. |

## Custom Blocks

A write needs one block of the text for each block of the document. Thus, the markdown and HTML export of a custom block type must read back as one block of that type, or as no block. If the export of a block gives more than one block (for example two paragraphs), `updateDocument` throws an error that names the block type. To fix it, make the `toExternalHTML` of the block type give one element that its `parse` rule reads back.

## Example Server

The [text lens server example](https://github.com/TypeCellOS/BlockNote/tree/main/examples/02-backend/05-text-lens-server) is an HTTP server with Hono. It gives a document as BlockNote JSON, markdown, HTML and plain text, and accepts a changed document back in each format. It keeps the versions in memory, and gives the version of a document as its `ETag`. A write sends that ETag in `If-Match` for a strict write (412 if another user changed the document), or in `Base-Version` for a merge (a merge with a conflict does not apply, unless the request has `On-Conflict: keep-current`). For `If-Match`, the server compares the ETags and then writes with `base: "current"`: a server with version numbers needs no stored document for a strict write. The response of a write gives the ETag of the document that the client wrote: use it as the base of the next write. A read gives the current document, with the changes of other users, and its ETag.

## How It Works

<ThemedImage
  src={{

  }}
  className="my-4"
  alt="The pipeline: project the document, parse the text, align the blocks, merge and plan the target document, diff it into operations, and apply them."
  width={900}
  height={395}
/>

1. **Project**: the document goes through the format and back. The result is the view: the document as the format shows it. The format loses the block IDs, but not the order of the blocks: each document block gives one view block or none, in document order. Thus, each view block links to the document block that gave it. To find out if a block gives a view block, the block goes through the format by itself. A block that the view shows as it is needs no such round trip.
2. **Parse**: the text of the client gives the blocks of the text.
3. **Align**: the view blocks and the blocks of the text pair by the location of their text: first the blocks with the same text and the changed blocks that stay in order, then the blocks between these pairs (see [Which Block Is the Same Block](#which-block-is-the-same-block)).
4. **Merge and plan**: each pair merges three ways. The base is the view block, "ours" is the block of the text, and "theirs" is the document block. A field that the text changed takes the value of the text. Other fields keep the value of the document, thus data that the format does not show stays. The result is the target document.
5. **Diff**: the target document and the document give the operations, by block ID. A strict write first compares `base` with the current document, and stops if they are different. In a merge, the target is for `base`: it first merges with the current document (a three-way merge of the documents), and the diff is against the current document.
6. **Apply**: the operations become the smallest ProseMirror steps. Unchanged text keeps its identity and its comments, and a collaboration binding sees only the small changes.
