# Text Updates

With text updates, a client can read a document as markdown, HTML or plain text, change the text, and write it back. An example is an AI agent or a script that edits documents as text, or an HTTP API with a `GET` and a `PUT` for each format.

A write does not replace the document. It applies only the changes of the text. Block IDs, colors, alignment, styles that the format does not show, nesting, and comments on text that did not change stay.

## Installation

```bash
npm install @blocknote/xl-ai
```

The text updates are in the `@blocknote/xl-ai/text-lens` entry point. On a server, the markdown and HTML conversions need a DOM (see [Server-side Processing](/docs/features/server-processing)). For a Y.Doc, also install `yjs` (see [Y.Doc](#ydoc)).

## Read and Write Text

```typescript
import { BlockNoteEditor } from "@blocknote/core";
import {
  getDocumentText,
  markdownFormat,
  updateDocument,
} from "@blocknote/xl-ai/text-lens";

const editor = BlockNoteEditor.create({ initialContent });

// Read the document as markdown.
const markdown = getDocumentText(editor, markdownFormat);

// A client changes the markdown. Then write it back.
const result = updateDocument(editor, {
  format: markdownFormat,
  text: changedMarkdown,
  base: "current", // the client read the current document
});
if (result.error === undefined) {
  const { operations, warnings } = result;
}
```

`base` is the version that the client read. `"current"` is correct if no other writer can change the document between the read and the write, for example if the read and the write occur in the same tick. Else, give the version that the client read (see [Writes From an Older Version](#writes-from-an-older-version)).

`updateDocument` applies the changes in one transaction. `operations` lists the changes by block ID, and `warnings` lists changes that did not apply as written (see [Warnings](#warnings)). To compute the operations, but not apply them, use `computeOperations` with the same change. Then `applyOperations(tr, operations)` applies them to a transaction of your own, for example to show them as suggestions.

If the text gives blocks that do not fit the schema of the editor, the result is `{ error: "invalid-document" }`, and the document does not change. An example is an HTML table cell that spans more rows than the table has.

The formats are `markdownFormat`, `htmlFormat` and `plainTextFormat`. HTML shows more data than markdown (for example colors and underline), thus a client can also change that data. In HTML, some data shows two times: as a `data-*` attribute and in the visible markup (for example `data-text-alignment` and `style="text-align: …"`, or `data-caption` and `<figcaption>`). The parse reads the attribute. Thus, to change such data, change the `data-*` attribute too.

## Which Block Is the Same Block

The text does not contain block IDs. The identity of a block follows the location of its text:

1. Two blocks are the same block if each one is the best match of the other, and they share at least half of the letters and digits of the shorter block. One comparison of all the words of the document decides this. Thus, a block with equal text is the same block, and a paragraph with many new sentences keeps its ID and props. If a block moves past changed blocks, the changed blocks also keep their IDs.
2. A block that the text moves keeps its ID, if no other block has the same text.
3. If one block on each side stays between two pairs, the two blocks are the same block. Thus, a paragraph with fully new text at the same position keeps its ID.

A split paragraph keeps its ID on the part with most of its text. Two joined paragraphs keep the ID of the first paragraph.

## Writes From an Older Version

A client can take time to change the text, for example an AI agent. Other users can change the document in that time. Give the document at the version that the client read as `base`. Then the write keeps the changes of the other users:

```typescript
const { text, base } = {
  text: getDocumentText(editor, markdownFormat),
  base: editor.document, // keep this version, for example in your version history
};

// ... later, after other users changed the document:
updateDocument(editor, {
  format: markdownFormat,
  text: changedText,
  base,
});
```

The client's changes apply to the current document, by block ID. If both sides changed the same part of a block (for example the same words, or the same prop), the change of the other user stays, and the client gets the warning `conflicting-change`. Thus, a write from an older version never reverts a change that it did not see. If the client removes a block that another user changed, the block stays, with the warning `removed-changed-block`. With `base: "current"`, the text applies to the current document without a merge, thus a text from an older version changes the newer changes back.

`base` must be the full document (BlockNote JSON) of that version. A version history keeps full documents anyway, because only a full document shows props and nesting.

### Reject Conflicts

Some clients must not lose a change, for example a tool that syncs a file that a person edits. For them, set `onConflict: "reject"`. Then a write with a conflict changes nothing, and the result is an error with the conflicts. The client can show them, or read the document again:

```typescript
const result = updateDocument(editor, {
  format: markdownFormat,
  text: changedText,
  base,
  onConflict: "reject",
});
if (result.error === "conflict") {
  // result.conflicts: the warnings `conflicting-change`, `removed-changed-block`
  // and `change-to-removed-block`, with the block IDs.
}
```

The default is `onConflict: "keep-current"`: the other changes of the client apply, and the result has the warnings. `onConflict` needs a version as `base`, because a write with `base: "current"` has no conflicts. A change as BlockNote JSON and the Y.Doc write have the same option.

## BlockNote JSON

`updateDocument` and `computeOperations` also take a full document as BlockNote JSON: `{ document, base }` in place of `{ format, text, base }`. The JSON contains the block IDs, thus the blocks pair by ID. Only the changed blocks and fields change, and with `base`, the changes of other users stay. A field that the JSON of a block does not have gets its default value, thus send each block with all its fields:

```typescript
import { updateDocument } from "@blocknote/xl-ai/text-lens";

const result = updateDocument(editor, {
  document: changedBlocks,
  base,
});
```

A block without an ID is a new block. An ID can identify only one block. Thus, a document with two blocks with one ID gives the error `invalid-document`. With `base`, a block also gets a new ID if another user added a block with that ID after the client read the document.

If the JSON does not fit the schema of the editor, the result is `{ error: "invalid-document" }`, as for a text. Examples are an unknown block type or style, and a prop value that the block type does not have.

## Y.Doc

For a collaborative document in a Y.Doc, use `updateYDoc` of the `@blocknote/xl-ai/text-lens/yjs` entry point. It takes the same change as `updateDocument` (a text or BlockNote JSON). The lens writes through an editor that is bound to the Y.Doc, as a client. Create it with `withCollaboration`, with the schema and the extensions of your other clients, and mount it: the Yjs binding works in the editor view. On a server, mount it on an element that is not in a page. `base` is `"current"`, or the Yjs state of the version that the client read:

```typescript
import { BlockNoteEditor } from "@blocknote/core";
import { withCollaboration } from "@blocknote/core/yjs";
import * as Y from "yjs";
import { getDocumentText, markdownFormat } from "@blocknote/xl-ai/text-lens";
import { updateYDoc } from "@blocknote/xl-ai/text-lens/yjs";

const fragment = ydoc.getXmlFragment("document-store");
const editor = BlockNoteEditor.create(
  withCollaboration({
    collaboration: { fragment, user: { name: "Server", color: "#888888" } },
  }),
);
editor.mount(document.createElement("div"));

const text = getDocumentText(editor, markdownFormat);
const base = Y.encodeStateAsUpdate(ydoc);

// ... later:
const result = updateYDoc(editor, fragment, {
  format: markdownFormat,
  text: changedText,
  base,
});
if (result.error === undefined) {
  // Send `result.update` to the other clients, if no provider does that.
}
```

When an editor binds to a Y.Doc, the Yjs binding removes the content that the schema of the editor cannot read. Thus, give the editor the same schema and extensions as your other clients (for example comments).

The write merges with the changes of other users by block ID, as for a document without Yjs. The Yjs binding (y-prosemirror v13) has limits for moves: if two users move the same block at the same time, the block can be there two times.

With `merge: "yjs"`, Yjs merges the write instead. The changes of the client apply to a copy of the Y.Doc at `base`, and Yjs merges that copy into the Y.Doc. This option needs a Yjs state as `base`. It does not allow `onConflict`, because Yjs merges without conflicts. With y-prosemirror v13, this option has more limits. A change of another user can be lost if the client moves, splits or joins the block, or changes its type. Also, a block that the client removes goes, with the changes of other users in it.

## Warnings

A result can contain these warnings:

| Warning                     | Meaning                                                                                                                                                                     |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `multi-part-block-replaced` | The format shows the block as more than one block (for example a code block with blank lines, in plain text), and the text moved, removed or split a part. The blocks of the text replace the block. A change of the text of the parts merges into the block, without this warning. |
| `unlinked-block-changed`    | The text changed a part of the text that does not come from one block. The change does not apply.                                                                           |
| `block-shape-replaced`      | The format shows the block with content of a different shape (for example a table as text), and the text changed it. The block becomes a block of the text.                 |
| `change-to-removed-block`   | The client changed or moved a block that another user removed. The change does not apply.                                                                                   |
| `removed-changed-block`     | The client removed a block that another user changed (or a block in it). The blocks with a change of the other user stay.                                                  |
| `conflicting-change`        | The client and another user changed the same part of a block (a part of its text, a style, a prop, its parent or its place). The change of the other user stays there.     |
| `merged-cells-removed` | A table lost its merged cells. Markdown and plain text show merged cells as separate cells, thus a change of the table there removes them. |

## Example Server

The [text lens server example](https://github.com/TypeCellOS/BlockNote/tree/main/examples/02-backend/05-text-lens-server) is an HTTP server with Hono. It gives a document as BlockNote JSON, markdown, HTML and plain text, and accepts a changed document back in each format. It keeps the versions in memory, and uses the `Base-Version` header for writes from an older version. The response of a write gives the document after the write, with the changes of other users, and its version for the next write.

## How It Works

<ThemedImage
  src={{
    light: "/img/features/text-updates/pipeline-light.svg",
    dark: "/img/features/text-updates/pipeline-dark.svg",
  }}
  className="my-4"
  alt="The pipeline: project the document, parse the text, align the blocks, merge and plan the target document, diff it into operations, and apply them."
  width={900}
  height={395}
/>

1. **Project**: the document goes through the format and back. The result is the view: the document as the format shows it. Most view blocks show a document block as it is: the same text at the same place. Each other block also goes through the format alone. Thus, each view block links to the document block that gave it.
2. **Parse**: the text of the client gives the blocks of the text.
3. **Align**: the view blocks and the blocks of the text pair by the location of their text (see [Which Block Is the Same Block](#which-block-is-the-same-block)).
4. **Merge and plan**: each pair merges three ways. The base is the view block, "ours" is the block of the text, and "theirs" is the document block. A field that the text changed takes the value of the text. Other fields keep the value of the document, thus data that the format does not show stays. The result is the target document.
5. **Diff**: the target document and the document give the operations, by block ID. For an older `base`, the target first merges with the current document (a three-way merge of the block trees), and the diff is against the current document.
6. **Apply**: the operations become the smallest ProseMirror steps. Unchanged text keeps its identity and its comments, and a collaboration binding sees only the small changes.
